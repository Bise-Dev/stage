Three architectural approaches

Picking shapes sync engine, worker model, and data persistence

A · Minimalist Django

Sync: Direct write-through. Webhook view writes mirror rows. Local action calls API, then writes mirror row.

Worker: None. Background threads for long ops.

UI sync: Server-Sent Events from Django views.

DB: SQLite, normalized tables.

Pros: smallest surface, fastest to ship, easiest to grok.

Cons: API failure mid-action = inconsistency, no retry, races between webhook and action are subtle.

B · Mirror + Outbox recommended

Sync: Github state mirrored as Django models. Local mutations append to an Outbox table, drained by worker which calls gh/API and updates mirror. Webhooks update mirror directly + emit reconciliation deltas.

Worker: django-q (in-process, SQLite-broker) for outbox drain + reconciliation poll fallback.

UI sync: Server-Sent Events.

DB: SQLite, mirror tables + outbox + sync state.

Pros: resilient to API failure, retries free, audit-able outbox, clean separation of concerns. Most Django-idiomatic.

Cons: ~30% more code than (A), worker lifecycle to manage.

C · Event-sourced

Sync: All state changes are events appended to an event log. Mirror rows are projections rebuilt from events. Github webhooks + local actions are both event sources.

Worker: django-q for projection rebuild + outbox.

UI sync: django-channels (websocket) since events naturally stream.

DB: SQLite or postgres, event_log + projections.

Pros: full audit, replay debugging, time-travel UI, easy to add new projections.

Cons: 2-3× the code, overkill for v1 single-user tool, more concepts to learn.

Why B (recommended)

  • Outbox solves race: "local action vs concurrent webhook"
  • Reconciliation poll = mandatory fallback (webhooks fail), worker already there
  • SSE simpler than channels for v1 UI sync
  • Outbox failures = visible to user (sync indicator on workspace)

Tradeoff vs A

  • A may bite hard the first time a webhook drops a comment-creation event mid-action
  • Once you need retries, you've reinvented half of B
  • django-q in-process is a small dep, not heavy infra
