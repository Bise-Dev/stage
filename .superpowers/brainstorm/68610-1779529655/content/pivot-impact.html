Pivot · "Local" backend → shared deployable service

DB = source of truth. Multi-user. Hosted later.

HOLDS (unchanged)
  • D1 Workspace = PR-scoped
  • D3 Sync = event-driven (webhooks + reconciliation poll)
  • D6 Own-PR review = self-walkthrough + optional AI-doc ingestion
  • D7 Architecture = Mirror + Outbox + Audit log
  • D8 Lifecycle ops are first-class
  • D9 Idempotency model (Outbox)
  • 4 aggregates (Mirror · Workspace · Drafts · Sync infra)
  • Most mirror entities (PR · Comment · Review · CheckRun · WorkflowRun · Thread)
CHANGES
  • D2 (storyline transport) · NO git-file transport. Storyline = DB row. Author writes via API; reviewer reads via API. No .local-review/storyline.json commit.
  • D4 (webhook ingress) · Production = public URL natively. Tunnel/smee = dev-only.
  • D5 (auth) · Server can no longer rely on one user's gh token. Need per-user auth.
  • DB · SQLite OK for dev, but design must allow Postgres for prod.
  • Drafts · Per-user, not per-workspace.
  • Local annotations · Per-user.
  • Storyline · Owned by PR author; access-controlled.
  • AI-doc · Ownership rule needed (author only? any contributor?).

NEW decisions to make

1. Auth flow shape           Github OAuth App? Github App (installation)? Hybrid?
2. Token storage             Encrypted at rest in DB. Per-user github access_token.
3. Workspace access control  Derived from github PR access (call API to check)
                             vs explicit Workspace.members
4. Roles                     PR author = can edit storyline / AI-doc / merge
                             Anyone with PR access = can comment / review / observe
5. Per-user state            DraftReview + LocalAnnotation keyed by (workspace, user)
6. Concurrency on storyline  Single editor (author) → simple. Otherwise needs locking.
7. Deploy target             Dev = local SQLite + tunnel. Prod = Postgres + public URL.
                             Same code, env-driven config.
8. Webhook subscription      One webhook per repo, shared by all workspaces of that repo.
                             Ref-counted by workspace existence.
9. SSE / realtime broadcast  Per-workspace channel, fan-out to subscribed users.
10. Session model            Django sessions + github OAuth login. CSRF + secure cookies.

What collapses (simpler now)

  • No git-commit of metadata → no branch protection, no signed-commit issues, no auto-push, no "stale storyline because not pushed yet" problem.
  • No per-workspace git worktree needed for metadata transport (worktree may still be useful for on-demand file content fetching, but optional).
  • Cross-user transport is solved by HTTP + DB — no clever workaround needed.

What gets harder

  • Auth + authz layer (Django OAuth flow, encrypted token storage, route guards).
  • Multi-user concurrency on shared workspace data (storyline edits, AI-doc updates).
  • Tenant model — who can see which workspace? derived live from github API or cached?
  • Deployment cost / responsibility (TLS, secrets, observability).
  • Per-user rate limit on github API (each user spends their own budget).
