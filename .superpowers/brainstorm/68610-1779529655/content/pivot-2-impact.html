Pivot 2 · Middleware-only backend

Github = data source of truth. Backend owns ONLY tool-native enhancement: storyline + intros + AI-doc.

HOLDS
  • D1 Workspace = PR-scoped pointer (just identity)
  • D2 Storyline = DB row
  • D5 Admin PAT for github API · OAuth-login for identity
  • D6 Self-walkthrough + AI-doc ingestion
  • D8 Lifecycle ops via backend (but as proxy, not mirror)
  • D10 Shared deployable, but DB-truth is now narrowed to tool-native data only
  • D11 Per-user state still applies to IntroComment + LocalAnnotation (if kept)
  • D12 SQLite dev / Postgres prod
  • D13 Permissive authz · storyline edit = PR author identity
DROPPED
  • D3 Event-driven sync · gone
  • D4 Webhook ingress · gone (no tunnel needed in v1)
  • D7 Mirror + Outbox + Audit log · gone
  • D9 Outbox-based idempotency · gone (ETag on storyline writes still applies)
  • D14 Webhook subscription lifecycle · gone
  • All mirror tables (PullRequest, DiffFile, Review, Comment, Thread, CheckRun, WorkflowRun, GithubUser)
  • SyncEvent / Outbox tables
  • Reconciliation loop · gone
  • django-q · probably not needed in v1
  • DraftReview / DraftComment if we adopt github native pending-review drafts (open Q)

Three open questions before I update the spec

  • Q-A: Drop DraftReview/DraftComment and use github native pending review drafts? (Github stores them, we just call POST .../reviews incrementally then submit.)
  • Q-B: Keep LocalAnnotation (per-user private notes that never sync)? Or drop for v1?
  • Q-C: Github read caching strategy: no cache (always fresh, simplest) · conditional ETag cache (60s window, cheap revalidation) · per-route choice?

What feels potentially wrong about this

  • Every UI render hitting github = high latency tax. ETag cache mitigates but a "fully fresh on each click" UX may feel slow on remote backend.
  • Github API rate limit (5000/h on PAT) shared across all users + all workspaces. A team of 10 active reviewers each browsing 3 PRs simultaneously could burn through quickly. Cache helps; this needs measurement.
  • No realtime sense of "someone just commented on this PR while you're looking at it". User must click refresh.
  • If we want even basic "live new comments" UX, we'd add SSE-driven server-side polling on backend per active workspace — re-introducing some of the loops we just deleted, but much lighter.
