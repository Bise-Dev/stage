# Repo access gate via an affirmative GitHub App installation check

When Stage's GitHub App isn't installed on a repo's owner (or the repo isn't selected in the installation), GitHub answers `repo_overview`'s `search_issues` with **`200` and empty results** rather than an error — so the Workspaces overview silently rendered empty (the canonical victim was the private repo `Bise-Dev/stage`). Because there's no exception to react to, we gate `repo_overview` with an **affirmative up-front check** (run before the GitHub fan-out, not a probe-on-failure): `GET /user/installations` must contain an installation whose `account.login` matches the repo owner (case-insensitive), and `GET /user/installations/{id}/repositories` must contain `{owner}/{repo}`. Both calls authenticate with the **user-to-server token** `GithubGateway` already holds — we deliberately did **not** use `GET /repos/{o}/{r}/installation` or app-JWT auth (`mint_installation_token` stays `NotImplementedError`), avoiding a `pyjwt`/crypto dependency for a check that the user token can already answer. A failed gate raises `ApplicationError(status=403, extra={"code": "github_app_no_access", "owner", "repo", "reason", "install_url"?})` — no partial payload; the whole overview is the 403 — and the client lifts that code into a targeted `RepoAccess` error variant to render an "Install the Stage App" CTA (the `install_url` is omitted, message-only, while `GITHUB_APP_SLUG` is still the placeholder). A transport/5xx on the installation calls is a *distinct* `502` ("couldn't check"), never conflated with the `403` ("definitely no access"). The gate runs inside `repo_overview`, which only executes on the existing 30s overview-cache **miss**, and the API caches only on success — so the `403` is never cached and the overview recovers the instant the app is installed.

## Considered Options

- **Catch the `404`/`403` on failure (probe-on-failure)** — rejected: the real failure mode is a silent `200`-with-empty-results from `search_issues`, which produces no exception to catch. Detection has to be a positive check.
- **`GET /repos/{o}/{r}/installation` (the direct "is this repo installed" endpoint)** — rejected: it requires app-JWT auth, which would mean implementing `mint_installation_token` and adding a JWT/crypto dependency. The user-to-server token already answers the question via `/user/installations`.
- **Render a partial overview with a warning** — rejected per the project's fail-loud rule (CLAUDE.md "Error handling"): no partial-success payloads. The overview is either complete or a clear `403`.
